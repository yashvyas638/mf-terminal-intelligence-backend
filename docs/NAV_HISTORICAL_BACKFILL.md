# AMFI historical NAV backfill — implementation contract

## Verified source facts

- AMFI's official NAV Download page exposes a NAV History form with mutual-fund, type, from-date and to-date selections.
- AMFI explicitly limits each historical NAV download to a maximum period of 90 days.
- The official latest NAV text report is available at https://portal.amfiindia.com/spages/NAVAll.txt.
- The inspected official report uses a six-column semicolon-delimited header: scheme code, two ISIN fields, scheme name, NAV and date. The parser now has a fixture based on actual rows from this official report.
- Official NAV Download page: https://www.amfiindia.com/net-asset-value/nav-download

The latest NAV report format is fixture-tested. This does not establish that the historical NAV form uses the same endpoint or identical payload contract. The historical form's HTTP method, endpoint parameters, fund/type identifiers, response headers and payload variants remain unverified. No guessed query string is wired into production.

## Delivered

- Deterministic inclusive date-window planner; every history request window is at most 90 calendar days.
- Contiguous ranges with no overlap or missing dates.
- Stable SHA-256 window keys for idempotent job/checkpoint identity.
- Resume helper that skips windows already marked complete.
- Official six-column latest-feed fixture and expanded eight-column compatibility fixture.
- No network calls, database writes, schema changes, or production historical ingestion in these foundation changes.

## Required next implementation gates

1. Capture a real request generated by AMFI's own NAV History form for one known AMC and a short date range.
2. Verify response format and that it matches selected AMC/type/date filters.
3. Add parser fixtures from that official historical response.
4. Add durable per-window checkpoints, attempt count, source hash, row counts and error class; mark complete only after transaction commit.
5. Add idempotent persistence keyed by scheme code + NAV effective date, retaining correction provenance.
6. Add bounded retries, backoff, rate limiting, pause/resume and operator visibility.
7. Reconcile planned windows, fetched windows, parsed rows, inserted/updated/unchanged rows and per-scheme coverage.
8. Run full migration and workload in staging before production backfill.

## Safety

- Do not infer the AMFI history form parameter mappings from third-party examples.
- Do not treat HTTP 200 as proof of correct date/AMC/type filtering.
- Do not overwrite current NAV rows with incomplete or unvalidated batches.
- Do not fabricate dates for weekends/holidays or interpolate missing NAVs.
- No production historical backfill until source-contract validation, staging reconciliation and an explicit operator go-ahead are complete.
