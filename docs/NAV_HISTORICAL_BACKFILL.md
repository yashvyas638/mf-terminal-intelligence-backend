# AMFI historical NAV backfill — implementation contract

## Verified source facts

- AMFI's official NAV Download page exposes a NAV History form with mutual-fund, type, from-date and to-date selections.
- AMFI explicitly limits each historical NAV download to a maximum period of 90 days.
- The official latest NAV text report is available at https://portal.amfiindia.com/spages/NAVAll.txt.
- The inspected official report uses a six-column semicolon-delimited header: scheme code, two ISIN fields, scheme name, NAV and date. The parser now has a fixture based on actual rows from this official report.
- Official NAV Download page: https://www.amfiindia.com/net-asset-value/nav-download

The latest NAV report format is fixture-tested. This does not establish that the historical NAV form uses the same endpoint or identical payload contract. The candidate portal request observed in independent community implementations is a GET to `https://portal.amfiindia.com/DownloadNAVHistoryReport_Po.aspx` with `tp`, `frmdt` and `todt` query parameters, returning an eight-column semicolon-delimited history layout. This is not an official AMFI API specification: the exact `tp` mapping, response behavior, and date/selection semantics still require a live comparison against the official History form before production use. The isolated adapter in `app/nav_history_source.py` implements bounded requests and strict response validation, but is not connected to a scheduled or production backfill.

## Delivered

- Deterministic inclusive date-window planner; every history request window is at most 90 calendar days.
- Contiguous ranges with no overlap or missing dates.
- Stable SHA-256 window keys for idempotent job/checkpoint identity.
- Resume helper that skips windows already marked complete.
- Official six-column latest-feed fixture and expanded eight-column compatibility fixture.
- Isolated candidate HTTP adapter with locale-independent date formatting, 90-day/type validation, bounded streaming, transient retries, HTML/empty-response rejection, and requested-window validation.
- Adapter tests use mocked HTTP responses; no live AMFI historical request has yet been validated, and the adapter is not connected to production ingestion.

## Current execution boundary

- The service is currently a tested application service, not an operator-facing API or scheduled job.
- Both execution gates must remain closed until a real request captured from AMFI's official History form has been compared with the adapter for the same type and date range.
- Planning a backfill makes no network requests and is safe to run in an isolated environment.

## Required next implementation gates

1. Capture a real request generated by AMFI's own NAV History form for one known AMC and a short date range.
2. Compare the isolated adapter's response against the official form for the same selected type and date range.
3. Verify response format and that it matches selected AMC/type/date filters.
4. Add parser fixtures from that official historical response.
5. Add durable per-window checkpoints, attempt count, source hash, row counts and error class; mark complete only after transaction commit.
6. Add idempotent persistence keyed by scheme code + NAV effective date, retaining correction provenance.
7. Add bounded retries, backoff, rate limiting, pause/resume and operator visibility.
8. Reconcile planned windows, fetched windows, parsed rows, inserted/updated/unchanged rows and per-scheme coverage.
9. Run full migration and workload in staging before production backfill.

## Safety

- Do not infer the AMFI history form parameter mappings from third-party examples.
- Do not treat HTTP 200 as proof of correct date/AMC/type filtering.
- Do not overwrite current NAV rows with incomplete or unvalidated batches.
- Do not fabricate dates for weekends/holidays or interpolate missing NAVs.
- No production historical backfill until source-contract validation, staging reconciliation and an explicit operator go-ahead are complete.
